# Governance

FinishBit uses a maintainer-led, contribution-driven governance model. The goal is to make decision ownership explicit while keeping design discussion and rationale visible to the community.

## Roles

### Users

Anyone who uses FinishBit, reports a problem, requests a capability, or participates in project discussion.

### Contributors

Anyone whose documentation, code, design, testing, triage, or other work is accepted into the project. Contributor status grants recognition, not merge or release authority.

### Maintainers

Maintainers review and merge changes, manage releases and security reports, enforce project policies, and decide when proposals are ready. Current ownership is recorded by repository access and [CODEOWNERS](.github/CODEOWNERS).

## Decision process

Routine fixes and documentation changes are decided through pull-request review. Significant changes—new public protocols, compatibility breaks, trust-boundary changes, major dependencies, or broad architectural work—begin with a GitHub issue so alternatives and migration impact can be discussed before implementation.

Maintainers seek rough consensus based on user value, project scope, maintainability, compatibility, and security. Consensus does not require unanimity. When discussion does not converge, the responsible maintainer makes and documents the decision and its rationale.

Private security decisions may remain confidential until coordinated disclosure. The public record should be completed after disclosure when doing so is safe.

## Maintainer responsibilities

Maintainers are expected to:

- act in the project's long-term interest and disclose relevant conflicts;
- apply contribution and conduct rules consistently;
- review compatibility, supply-chain, and security effects before merging;
- avoid promising delivery dates without a committed release plan;
- preserve attribution and license notices;
- recuse themselves when a conflict prevents impartial review.

## Becoming or removing a maintainer

Maintainers may invite a sustained contributor after evaluating technical judgment, review quality, reliability, communication, and conduct over time. There is no contribution-count threshold.

Maintainer access may be removed for inactivity, voluntary resignation, repeated policy violations, compromised credentials, or actions that materially endanger the project. When confidentiality permits, the reason is recorded for the remaining maintainers.

## Project changes

This governance document may evolve through a focused pull request. Changes that materially alter contributor rights, licensing, or project control require explicit maintainer approval and prominent release communication.
